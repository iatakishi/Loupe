# Loupee Bot — Telegram Bargain Analyzer

Part of the **Bina.az Real-Time Bargain Finder** capstone project (Holberton School ML).
This repository covers the **MLOps / Backend (Alert & Demo)** role: the Telegram bot that lets users check whether a Bina.az listing is priced below its estimated market value.

## What this bot does

A user sends the bot a Bina.az listing link. The bot looks up that listing in the team's pre-computed predictions dataset and replies with a formatted analysis: the listing's actual price, the model's predicted price, and how much of a bargain (or not) it is.

**Current status:** fully working, using the **real dataset and real model predictions** (`predictions.json`), generated by the team's CatBoost model (`model/train.py`). This is an on-demand lookup tool, not a live-scraping or auto-push system — see "Design notes" below for why.

## How it works (pipeline)

```
predictions.json  --->  scoring.py  --->  alerts.py  --->  bot.py (Telegram)
 (real model output)     (lookup)        (message text)    (replies to user)
```

1. **`predictions.json`** — generated by the team's model (`model/train.py`), contains every scraped listing along with its predicted price and bargain score, keyed by listing URL.
2. **`scoring.py`** — loads `predictions.json` into memory and looks up a listing by URL.
3. **`alerts.py`** — formats a listing's data into the readable Telegram message the user sees.
4. **`bot.py`** — runs the Telegram bot: handles `/start`, `/stats`, and any message containing a Bina.az link, replying with the analysis.
5. **`storage.py`** — SQLite persistence layer, tracks unique users for `/stats` (survives bot restarts).
6. **`get_listingUrl.py`** — a standalone testing helper (not used by the bot itself), pulls a random real listing URL from `predictions.json` for manual testing/demos.

## Bargain Score logic

```
bargain_score = (predicted_price - actual_price) / predicted_price * 100
```

| Score          | Alert level      |
|----------------|------------------|
| >= 15%         | `very_cheap`     |
| 10% – 15%      | `below_market`   |
| < 10%          | `none`           |

## Setup

1. **Get a bot token** from [@BotFather](https://t.me/BotFather) on Telegram (`/newbot`).
2. **Create a virtual environment:**
   ```bash
   python -m venv venv
   ```
3. **Activate it:**
   - Windows: `venv\Scripts\activate.bat`
   - Mac/Linux: `source venv/bin/activate`
4. **Install dependencies:**
   ```bash
   pip install -r requirements.txt
   ```
5. **Create a `.env` file** in this folder:
   ```
   TELEGRAM_BOT_TOKEN=your_token_here
   ```
6. **Make sure `predictions.json` is present** in this folder (pulled from `model/predictions.json` in the shared repo).

## Running the bot

```bash
python bot.py
```

You should see `Bot is running...` in the terminal. In Telegram:
- Send `/start` for a greeting (also registers you for `/stats`).
- Send `/stats` to see how many unique users have used the bot.
- Send any message containing a Bina.az listing link (e.g. `https://bina.az/items/6364416`) to get an analysis.
- Listings not present in `predictions.json` will get a "not found" reply instead of an analysis.

## Design notes — why on-demand, not auto-push

An earlier version of this bot auto-pushed alerts on a 30-second timer, scanning a static mock dataset. The team decided against this approach for the real version, since:

- The dataset is a static snapshot (`predictions.json`), not a live feed — auto-pushing from it repeatedly would either spam duplicate alerts or require complex dedup logic for something that isn't actually live data.
- A better user experience: letting a user check a *specific* listing they're already interested in, rather than pushing a fixed set of "underpriced" listings to everyone regardless of what they're looking for.

This is a deliberate design choice, not a limitation — see the team discussion in project notes for the full reasoning.

## Known limitations

- **Static dataset:** `predictions.json` is a one-time snapshot from the backfill scrape. It does not update automatically as new listings appear on Bina.az.
- **Ephemeral hosting state:** if deployed to a platform with an ephemeral filesystem, `bot_data.db` (and therefore the `/stats` count) may reset on redeploy, depending on the hosting platform's storage guarantees.

## Next steps

- Periodic re-scraping + re-scoring to keep `predictions.json` current.
- Persistent hosting-level storage (or an external database) so `/stats` survives redeploys, not just restarts.
